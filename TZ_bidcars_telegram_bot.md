# Техническое задание
## Telegram-бот для мониторинга новых лотов на bid.cars по пользовательским фильтрам

---

## 1. Назначение проекта

Бот позволяет пользователю прислать ссылку на страницу с результатами фильтра на сайте **bid.cars** (например, поиск по марке/модели/году/типу повреждения/цене). Бот периодически проверяет этот фильтр и присылает пользователю в Telegram карточки **новых** лотов, появившихся с момента последней проверки.

Ключевая логика: **не дублировать** уже показанные лоты, работать с **несколькими фильтрами на пользователя**, работать с **несколькими пользователями одновременно**.

---

## 2. Технологический стек

- **Язык:** Python 3.11+
- **Telegram-фреймворк:** aiogram 3.x (асинхронный, современный, хорошо документирован)
- **Парсинг HTML:** `httpx` (async HTTP-клиент) + `BeautifulSoup4` (`bs4`)
- **Рендеринг JS (если потребуется):** `playwright` (async) — использовать только если обычный HTTP-запрос не отдаёт нужные данные (см. п. 6.2)
- **База данных:** SQLite через `SQLAlchemy` (async, `aiosqlite`) — для MVP этого достаточно, миграция на PostgreSQL в будущем не должна требовать переписывания бизнес-логики
- **Планировщик задач:** `APScheduler` (async) — периодический опрос фильтров
- **Конфигурация:** `.env` файл + `pydantic-settings`
- **Логирование:** стандартный `logging`, ротация файлов через `RotatingFileHandler`

## 3. Функциональные требования

### 3.1 Команды бота

| Команда | Описание |
|---|---|
| `/start` | Приветствие, краткая инструкция |
| `/add_filter <ссылка>` | Добавить новый фильтр bid.cars для отслеживания |
| `/list_filters` | Показать список активных фильтров пользователя (с номерами/id) |
| `/remove_filter <id>` | Удалить фильтр по номеру из списка |
| `/pause_filter <id>` | Приостановить проверку фильтра (не удаляя) |
| `/resume_filter <id>` | Возобновить приостановленный фильтр |
| `/status` | Показать: сколько активных фильтров, когда была последняя проверка, сколько всего лотов найдено |
| `/set_interval <минуты>` | (опционально) задать частоту проверки для своих фильтров, с минимальным ограничением (см. п. 5.4) |
| `/help` | Список команд с описанием |

### 3.2 Логика добавления фильтра (`/add_filter`)

1. Валидация: ссылка должна вести на домен `bid.cars` и содержать путь поиска/фильтра (например `/ru/search/...` или `/ru/lots/...` — точный формат уточнить по факту, см. п. 6.1).
2. При добавлении бот **сразу** делает первый парсинг фильтра, чтобы:
   - Сохранить снимок текущих лотов в БД как "уже виденные" (чтобы не заспамить пользователя всей историей сразу)
   - Прислать пользователю сообщение: "Фильтр добавлен, сейчас по нему N лотов, буду присылать новые"
3. Сохранить фильтр в таблицу `filters` (см. п. 4) с привязкой к `user_id`.

### 3.3 Логика фонового опроса

1. Раз в `N` минут (глобальный дефолт, например 10 минут, настраивается в `.env`) планировщик проходит по всем активным (`is_paused = False`) фильтрам всех пользователей.
2. Для каждого фильтра:
   - Скачивает страницу результатов
   - Парсит список лотов (VIN/lot_id, марка/модель, год, цена, повреждение, ссылка на лот, миниатюра фото)
   - Сравнивает с уже сохранёнными в таблице `seen_lots` для этого фильтра
   - Новые лоты (которых не было в `seen_lots`) → отправляет пользователю карточкой, добавляет в `seen_lots`
3. **Rate limiting**: между запросами к bid.cars — пауза минимум 2-3 секунды, запросы разных фильтров не должны идти параллельно пачкой (см. п. 5.2).

### 3.4 Формат карточки лота в Telegram

Каждый новый лот отправляется отдельным сообщением (или медиа-группой, если фото несколько) в формате:

```
🚗 2018 BMW 530xi
💰 Текущая ставка: $625
🔧 Повреждение: Сторона, Задняя часть
🏁 Статус: На ходу
📍 Локация: [город, штат]
🔗 [Ссылка на лот]
```

Плюс превью-фото лота (если технически возможно вытащить прямую ссылку на изображение — см. п. 6.2).

### 3.5 Множественные пользователи и фильтры

- Один пользователь может добавить несколько фильтров (лимит — см. `.env`, например до 10 на пользователя, чтобы не перегружать парсер).
- Разные пользователи не видят фильтры друг друга.
- Если два пользователя добавили идентичный по URL фильтр — можно (как оптимизация, не обязательно для MVP) кэшировать результат парсинга на уровне фильтра, а не дублировать запрос к сайту дважды. Это опционально, для MVP допустимо просто парсить отдельно на каждого пользователя.

## 5. Нефункциональные требования

### 5.1 Обработка ошибок
- Если парсинг фильтра упал (сайт недоступен, изменилась вёрстка, timeout) — **не ронять весь цикл опроса всех фильтров**, залогировать ошибку, перейти к следующему фильтру.
- Если фильтр падает **N раз подряд** (например, 5) — прислать пользователю уведомление "Не могу распарсить фильтр, возможно ссылка устарела или сайт изменился" и автоматически поставить фильтр на паузу, чтобы не долбить сайт впустую.

### 5.2 Уважение к сайту-источнику
- User-Agent — указать реалистичный browser-like UA, не дефолтный `python-requests`.
- Соблюдать разумные паузы между запросами (см. 3.3).
- Обязательно ознакомиться и не нарушать грубо `robots.txt` и пользовательское соглашение bid.cars — автоматический сбор данных может быть ограничен условиями сайта; это должно использоваться для личных нужд, не для коммерческой переупаковки/перепродажи данных третьим лицам.

### 5.3 Безопасность
- Токен бота — только через `.env`, не хардкодить в коде.
- Не хранить никаких платёжных/личных данных пользователя, кроме `telegram_chat_id`.

### 5.4 Ограничения
- Глобальный минимальный интервал опроса — не менее 5 минут на фильтр (защита от слишком агрессивного парсинга), даже если пользователь просит чаще.
- Максимум фильтров на пользователя — задать константой в конфиге (например 10).

## 6. Открытые технические вопросы (требуют исследования в начале разработки, до полной реализации)

### 6.1 Формат URL фильтра bid.cars
Нужно на старте разработки вручную собрать 3-5 примеров реальных ссылок на фильтр/поиск с сайта (не на конкретный лот, а именно на список результатов с применёнными параметрами) и определить:
- Стабильна ли структура URL (query-параметры) между разными фильтрами
- Есть ли пагинация и как она выражена в URL

### 6.2 Рендеринг страницы: статический HTML или JS
Нужно проверить (например, через `curl` без JS или `httpx.get` и сравнить с тем, что видно в браузере):
- Приходят ли карточки лотов в исходном HTML-ответе сервера, или подгружаются JS-скриптом (XHR/fetch к внутреннему API)
- **Если данные приходят через отдельный XHR-запрос к внутреннему API bid.cars** (это частый случай для современных сайтов) — это на самом деле ЛУЧШИЙ сценарий: вместо парсинга HTML можно дёргать напрямую этот JSON API (найти его через вкладку Network в DevTools браузера), что быстрее, надёжнее и меньше ломается при редизайне сайта. Cursor должен исследовать это первым делом и по возможности использовать этот путь вместо BeautifulSoup-парсинга HTML.
- Если данные только в JS-рендере без доступного API — тогда переходить на Playwright (медленнее, тяжелее, но надёжно).

### 6.3 Формат данных лота
Определить, какие поля реально доступны в списке результатов (без захода на страницу конкретного лота) — вероятно: VIN, год/марка/модель, текущая ставка, тип повреждения, статус (на ходу/нет), фото (миниатюра), ссылка. Поля, которых может не быть в списке (только на странице лота): ACV/ERC, полная история продаж, детальные фото — для MVP их не тянуть, чтобы не делать лишний запрос на каждый лот.

## 7. Этапы реализации (для Cursor — рекомендуемый порядок работы)

1. **Разведка сайта** — вручную (через браузерные DevTools) изучить структуру фильтра и определить подход из п. 6.1–6.3. Написать отдельный тестовый скрипт `explore.py`, который просто скачивает и печатает/сохраняет сырой ответ для одного тестового фильтра.
2. **Модуль парсера** (`parser.py`) — функция `parse_filter(url: str) -> list[LotData]`, где `LotData` — dataclass/pydantic-модель с полями из п. 6.3. Покрыть базовыми unit-тестами на сохранённом заранее HTML/JSON-фикстуре (чтобы тесты не зависели от живого сайта).
3. **Модели БД** (`models.py`) — SQLAlchemy-модели по схеме из п. 4, миграции через Alembic (или просто `create_all` для MVP).
4. **Логика бота** (`bot.py` / `handlers/`) — обработчики команд из п. 3.1.
5. **Планировщик** (`scheduler.py`) — задача APScheduler, вызывающая парсер по всем активным фильтрам и рассылающая новые лоты.
6. **Конфиг и запуск** (`config.py`, `main.py`, `.env.example`).
7. **README.md** — инструкция по запуску (получение токена бота у BotFather, установка зависимостей, переменные окружения, запуск).

## 8. Критерии приёмки (Definition of Done для MVP)

- [ ] Пользователь может добавить ссылку на фильтр и получить подтверждение с текущим количеством лотов
- [ ] Через заданный интервал бот присылает новые лоты, появившиеся после добавления фильтра, без дублей
- [ ] Пользователь может посмотреть список своих фильтров, поставить на паузу/удалить
- [ ] При падении парсинга бот не падает целиком, ошибка логируется
- [ ] Есть `.env.example` и `README.md` с инструкцией по запуску с нуля
